# Billing 1: Database Updates

## Overview

Replace the unused `User.plan` / `User.stripe*` columns with a `SubscriptionPeriod` table that holds every billing fact, and derive the user's plan from it. No Stripe code in this step: when it lands, the app behaves as today, with Pro coming from granted periods (the seed's demo user).

Reference: `docs/stripe-integration-plan.md` ("Design decisions", "The period lifecycle", "Schema changes").

## Requirements

1. **R1** A `SubscriptionPeriod` table, one row per period of Pro, FK `userId` with `onDelete: Cascade`.
2. **R2** Each row has a `status`: `PENDING` (checkout started, not paid), `PAID`, `EXPIRED` (checkout abandoned). Only `PAID` rows can grant Pro.
3. **R3** A `PAID` row is live while `periodEnd + BILLING_GRACE_MS >= now`. (`revokedAt` was dropped on 2026-10-26: ending access early moves `periodEnd`.) The user is Pro when they have at least one live row.
4. **R4** `vendor` is nullable. No vendor means granted, not paid (free trials, the seed, comped accounts); such rows are never checked with a vendor.
5. **R5** Stripe-only columns are named for Stripe: `stripeCheckoutSessionId` (unique) and `stripePriceId`, both nullable.
6. **R6** `User.plan` and `User.stripeCustomerId`, `stripeSubscriptionId`, `stripePriceId`, `stripeCurrentPeriodEnd` are dropped. `enum Plan` leaves the schema; `Plan` becomes `"FREE" | "PRO"` in `src/types/billing.ts`.
7. **R7** `getCurrentUser()` derives `plan` / `isPro` from the newest live `PAID` period, from the database only (it never calls Stripe: it runs on every request, including image loads). It never returns a customer, subscription or checkout session id. The billing details the UI shows (interval, end date, whether the user is a vendor customer) go in the user session in spec 2.
8. **R8** The seed's demo user is Pro through a granted period (no vendor) ending far in the future, not `plan: 'PRO'`.

## Schema

```prisma
enum BillingVendor {
  STRIPE
}

enum BillingInterval {
  MONTH
  YEAR
}

enum PeriodStatus {
  PENDING // checkout started, not paid; grants nothing
  PAID
  EXPIRED // checkout abandoned (Stripe expires unpaid sessions after ~24 h)
}

model User {
  // `plan` and the four `stripe*` columns removed
  subscriptionPeriods SubscriptionPeriod[]
}

/// One period of Pro, from checkout to expiry. No vendor means granted, not paid.
model SubscriptionPeriod {
  id                      String          @id @default(uuid())
  userId                  String
  user                    User            @relation(fields: [userId], references: [id], onDelete: Cascade)
  status                  PeriodStatus    @default(PAID)
  vendor                  BillingVendor?  // null: granted, never checked with a vendor
  vendorCustomerId        String?         // cus_…, filled when paid; copied on renewals
  vendorSubscriptionId    String?         // sub_…, shared by every renewal
  stripeCheckoutSessionId String?         @unique // cs_…, Stripe's id for the checkout
  stripePriceId           String?         // price_…, what a Stripe period was bought at
  interval                BillingInterval
  periodStart             DateTime?       // null while PENDING
  periodEnd               DateTime?
  createdAt               DateTime        @default(now())
  updatedAt               DateTime        @updatedAt

  @@unique([vendor, vendorSubscriptionId, periodEnd])
  @@index([userId, status, periodEnd])
}
```

## Tests (write first)

- `plan-rules.test.ts`: R3 (live through `periodEnd + grace`, not a millisecond after).
- `session.test.ts`: R2, R3, R7 (`PENDING` / `EXPIRED` rows give Free; a live `PAID` row gives Pro; an expired one gives Free; no id fields in the result).

- Granted period: R4, R8 (a row with no vendor gives Pro while live).

## Notes

- Migrations only through `npm run db:migrate` on the dev branch, never `db push` or MCP DDL.
- The migration drops `User.plan`. Before merging, check whether any production user is `PRO` by hand; if so, give them granted periods in the migration. Ask before looking at production.
- Postgres treats `NULL`s as distinct, so the composite unique doesn't constrain pending or granted rows; `stripeCheckoutSessionId @unique` covers pending ones.
- A free trial will be a granted `PAID` row with a short `periodEnd`. "One trial per user" needs a marker, added when trials are built.
