# Billing 2: Stripe Setup and Core Code

## Overview

Enforce the Free plan's limits on the server, add the Stripe adapter behind a vendor-neutral interface, start checkouts as `PENDING` periods, settle them through a Stripe webhook, and check the user's subscription with Stripe once per session load. Builds on spec 1 (`SubscriptionPeriod`). UI comes in spec 3.

Reference: `docs/stripe-integration-plan.md` ("Architecture", "Files to create", "Security"). Where this spec and the plan doc differ, this spec wins: it adds the webhook back and moves the Stripe check from every request to the session load.

## Requirements

### Feature gating (independent of Stripe; can merge first)

1. **R1** A Free user can't create a 51st item (`PRICING.free.itemLimit`), counted inside `createItem`'s transaction; nothing is saved.
2. **R2** A Free user can't create a 4th collection (`PRICING.free.collectionLimit`), inside a transaction.
3. **R3** A Free user can't create a `file` or `image` item (`PRO_TYPE_NAMES`); checked in the action before the rate limit and the save.
4. **R4** Pro users have none of these limits. Refusals answer with messages that derive their numbers from `PRICING`. The plan comes from `getCurrentUser()` (database only, spec 1).

### Stripe adapter

5. **R5** `src/services/billing/stripe.ts` is the only module that imports `stripe` at runtime (boundaries test). It starts with `import "server-only"`, builds the client lazily with `apiVersion: "2026-09-30.endive"`, and throws `BillingNotConfiguredError` naming any missing `STRIPE_*` setting before calling Stripe.
6. **R6** It implements `BillingAdapter`: `createCheckout`, `fetchCheckout`, `fetchActivePeriod`, `hasOpenSubscription`, `parseWebhook`, `createPortalLink`, `cancelAll`, `cancelSubscription`. Period dates come from the subscription item's `current_period_start` / `current_period_end`.
7. **R7** `src/services/billing/vendors.ts` maps every `BillingVendor` to its adapter; `checkoutAdapter()` picks `BILLING_VENDOR` (default `stripe`) for new checkouts only.

### Starting a checkout

8. **R8** `startCheckout` (form action, hidden `interval`) first confirms the signed-in user's row exists (`requireCurrentUser()`, outside any `try`). On a Free user it inserts one `PENDING` period, creates a Checkout session with the period id as `client_reference_id`, in metadata, and in the idempotency key `checkout-{periodId}`, stores the returned `cs_…` id on the row, and redirects to the session URL.
9. **R9** A new user's email goes as `customer_email` (Checkout creates the customer on payment); a returning customer's id (from their latest paid row) goes as `customer`.
10. **R10** An open pending checkout is reused: the user is sent to the same session, and nothing is inserted. An expired one is marked `EXPIRED` and a new one started.
11. **R11** A returning customer with an open subscription at Stripe gets `BILLING_ALREADY_SUBSCRIBED`; a Pro user is redirected to settings; over the `checkout` rate limit (10 per hour, per user) gets a toast; missing config gets `BILLING_UNAVAILABLE` and nothing is written.
12. **R12** `success_url` is `/settings?billing=success` and `cancel_url` is `/settings?billing=canceled` on `APP_URL`. Neither carries an id.

### Webhook

13. **R13** `POST /api/billing/[vendor]/webhook` (one dynamic route; the adapter is looked up by the segment, unknown → 404) verifies the signature on the raw body (`await request.text()`) with `STRIPE_WEBHOOK_SECRET`; a missing or bad signature answers 400 and writes nothing.
14. **R14** `checkout.session.completed` (paid): finds the `PENDING` period whose `stripeCheckoutSessionId` matches **and** whose id equals the session's `client_reference_id`, and marks it `PAID` with Stripe's customer, subscription, price, interval and dates. Conditional on still `PENDING`, so a retried or duplicated event (and a session load racing it) changes the row once.
15. **R15** If no such period exists, or its user no longer exists (the account was deleted after the checkout started; periods cascade with the user), the new subscription is **cancelled at once** and the event logged. It never creates a user or a period.
16. **R16** `checkout.session.expired` marks the matching `PENDING` row `EXPIRED`. Other event types answer 200 and write nothing. A failure while writing answers 500, so Stripe retries.
17. **R17** `proxy.ts`'s matcher lets `/api/billing/*/webhook` through without a session (like `/api/auth/*`); every other `/api/*` route keeps its 401. The route is the one session-less writer: it is keyed by ids only a signed Stripe event supplies.

### Session load

18. **R18** On each session load (`getUserSession()`, run by the `(app)` layout on a full page load, not on navigation or every request), `resolveBilling(userId)` checks the user's latest record once, then Stripe once:
    1. The newest `PENDING` row with a session id: fetch the session; paid → mark `PAID` (same write as R14); expired → `EXPIRED`.
    2. Else the newest `PAID` row with a vendor customer, live or not: ask Stripe for the customer's active subscription. If Stripe has one whose period isn't stored yet (a renewal), insert a new `PAID` row in a `Serializable` transaction that first checks no row with that subscription and `periodEnd` exists.
    3. A user with no vendor rows (Free, or granted-only) makes no Stripe call.
19. **R19** The result is stored in the user session as `billing: { plan, interval, periodEnd, isCustomer }`, like `user`: read on the client with `useUserSession()`, never carrying vendor ids. Navigation reuses it; a full page load checks again.
20. **R20** A Stripe error answers from the stored rows only (a live period still gives Pro; nothing is granted without Stripe) and is logged. The check also obeys a `billingCheck` rate limit (30 per hour, per user); past it, the stored rows answer.
21. **R21** No file in `actions/` imports `services/billing/entitlement` (boundaries test): period writes are never reachable as a server action.

### Account deletion

22. **R22** `deleteAccount` cancels every open subscription of every customer the user paid through (`cancelAll`) before deleting the user; a Stripe failure keeps the account and answers with a message. A checkout still open in another tab that is paid later is caught by R15.

## Notes

- Call `requireCurrentUser()` outside any `try`; `redirect(url)` outside the `try` too, since it throws.
- If the session call fails after the `PENDING` row is inserted, the row has no session id and is skipped; a later checkout inserts a fresh one. Say so in a comment at the spot.
- `fake-prisma.ts` won't model isolation levels: unit tests cover the logic, and a comment at the renewal insert names the race and its guards (the existence check and the unique key).
- The webhook and the session load both settle through `settleCheckout()`, so they can't disagree; whichever runs first marks the row, the other finds it already `PAID`.
- Never delete Stripe prices (Stripe can't); archive with `stripe prices update <id> --active=false`.
