# Billing 3: UI, Checks and Testing

## Overview

Show billing to the user (settings Billing card, Checkout return, homepage CTA, sidebar badge, Pro-locked types), check the logic end to end, then test the whole flow in the Stripe sandbox with `stripe listen` running. Builds on specs 1 and 2.

Reference: `docs/stripe-integration-plan.md` ("Request flows", "Security", "Open decisions", "Later"). Where they differ, specs 1–3 win.

## Requirements

### UI

1. **R1** `/settings` gets a **Billing** card (`src/components/settings/BillingSection.tsx`) between Editor preferences and Change password, reading `useUserSession().billing` (spec 2, R19):
   - Free: two Upgrade buttons, monthly and yearly, each an `ActionForm` posting `startCheckout` with a hidden `interval`. Prices come from `PRICING` through `lib/pricing` (no typed amounts); yearly shows the saving.
   - Pro (paid): "Pro, monthly" or "Pro, yearly", "Paid through {periodEnd}" (dates through the locale helpers), and a **Manage billing** button posting `openBillingPortal` when `isCustomer`.
   - Pro (granted, no vendor): Pro and its end date, no Manage button.
2. **R2** Stripe's redirect back (`/settings?billing=success`) is a full page load, so the session load checks Stripe once (spec 2, R18) and settles the pending checkout if the webhook hasn't already. The page shows a success toast when the session says Pro, or a "payment is processing" toast when it doesn't yet, then drops the flag from the URL (`FlagToast`, as for `passwordChanged`).
3. **R3** `?billing=canceled` shows a neutral toast; the plan is unchanged.
4. **R4** The homepage Pro card's CTA goes to `signInHref(ROUTES.settings)` (signed-in users land on settings).
5. **R5** The sidebar PRO badge (`SidebarTypeNav.tsx`) is hidden for Pro users; remove its KNOWN DEVIATION comment.
6. **R6** The New Item dialog shows `file` and `image` as Pro-locked for Free users (with a link to settings) instead of letting them fill the form and fail. The server check (spec 2, R3) stays.
7. **R7** A Free user who hits a limit (51st item, 4th collection) sees spec 2's message as a toast from the New Item and New Collection dialogs.

### Logic checks

8. **R8** The return URLs carry only the flag; nothing in them is read as an id. Stripe's answer for the user's own stored session decides.
9. **R9** The user session (`user`, `billing`) never carries `vendorCustomerId`, `vendorSubscriptionId` or `stripeCheckoutSessionId`.
10. **R10** Pro checks in actions read `getCurrentUser()` (database only), and the session's `billing.plan` comes from the same rows after the once-per-load check, so the UI and the server agree after every full page load.

## Manual testing (sandbox, test login from `.env.example`)

Run `stripe listen --events checkout.session.completed,checkout.session.expired --forward-to localhost:3000/api/billing/stripe/webhook` beside `npm run dev`.

Cards: `4242 4242 4242 4242` succeeds; `4000 0025 0000 3155` asks for 3-D Secure; `4000 0000 0000 0002` is declined. Any future date, any CVC.

- [ ] Upgrade monthly, pay: `stripe listen` shows `checkout.session.completed` answered 200; lands on `/settings?billing=success` showing Pro; PRO badges gone; file and image unlocked; one `PAID` row with customer, subscription, price and dates.
- [ ] Stop `stripe listen`, upgrade and pay: still Pro on return (the session load settles it).
- [ ] Upgrade, pay, close the tab before the redirect: the webhook settles it; reopen the app and it shows Pro.
- [ ] Navigate between pages while Pro: no Stripe calls; a full reload makes one (Dashboard → Developers → Logs).
- [ ] Click Upgrade twice before paying: the same Checkout page; one `PENDING` row.
- [ ] 3-D Secure card: the challenge appears; success still upgrades.
- [ ] Declined card: Checkout shows the error; still Free; the row stays `PENDING`.
- [ ] Back out of Checkout: canceled toast; still Free.
- [ ] Bad signature: `curl -X POST localhost:3000/api/billing/stripe/webhook -d "{}"` answers 400; signed out, the webhook isn't answered 401 but other `/api/*` routes are.
- [ ] `stripe trigger checkout.session.completed` (a session no period matches): 200, nothing written, logged.
- [ ] Start a checkout, delete the account in another tab, then pay: the webhook cancels the new subscription (Dashboard shows it cancelled).
- [ ] Manage billing opens the portal (no plan switching); returning lands on settings.
- [ ] **Expiry, with a temporary fake date**: in the session load, temporarily replace "now" with a date past `periodEnd + grace` (or hard-code `billing.plan` / `isPro` to Free). Expect Free and Pro features locked: the Billing card shows Upgrade, file and image are locked, the 51st item is refused. **Revert before committing**; never commit the override.
- [ ] Cancel at period end in the portal: Stripe shows it cancelling; the app stays Pro (the fake-date check above covers what happens at the end).
- [ ] Free limits: 51st item and 4th collection refused with the message.
- [ ] Delete the account while subscribed: the subscription shows as cancelled in the Dashboard.
- [ ] The seed's demo user is Pro with no Manage button and causes no Stripe call.
- [ ] `node testScripts/stripe-price-check.mjs` passes.
- [ ] `npm test`, `npm run lint`, `npm run build` pass.

Renewals (a new `PAID` row when Stripe moves the period on) are covered by `entitlement.test.ts` (spec 2, R18.2), not by hand.

## Remaining (not in these specs)

- **Production**: live product and prices, a restricted key (`rk_live_…`), the live webhook endpoint `https://<domain>/api/billing/stripe/webhook` with its own `STRIPE_WEBHOOK_SECRET`, Vercel env (`STRIPE_SECRET_KEY`, both price ids, `STRIPE_WEBHOOK_SECRET`, `BILLING_VENDOR`, `APP_URL`), the live portal (no plan switching), one-subscription limit, branding and customer emails. Before merging, check whether any production user is `PRO` by hand (spec 1 drops `User.plan`); ask before looking at production.
- **Open decisions**: grace window (1 day suggested), "Renews on" vs "Cancels on" (needs `cancel_at_period_end`, available from the once-per-load Stripe call), env price ids vs lookup keys, `APP_URL` vs `VERCEL_URL`.
- **Later** (README "Future Plans"): trial users upgrading, plan switching, configurable payments, more vendors and payment methods; also an email change not reaching the Stripe customer.
