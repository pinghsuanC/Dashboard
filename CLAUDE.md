# Rules that must not change

Load-bearing; do not drop or soften. Other sections point here instead of repeating them.

## Production and data

- Always `npm run db:migrate`, never `prisma db push` unless explicitly asked. `.env` points at the Neon dev branch; production is a separate branch and only gets `db:deploy`.
- Neon MCP: pass both `project_id` and `branch_id` explicitly on every call, read-only ones included. The OAuth connection is not limited to one project, and leaving out `branch_id` hits the default branch, which is `production`.
- Neon ids: project `stashboard` `rough-wind-04171988`; branch `development` `br-silent-firefly-b4er4xcj`; production `br-polished-voice-b487lkfo`.
- Never touch `production` through the MCP: no reads, writes, migrations, `reset_from_parent`, branch or endpoint changes.
- If a task seems to need production (for example comparing schemas), stop and ask. Continue only if production is named explicitly in the request.
- Schema changes only through `npm run db:migrate` on the dev branch, never `run_sql` DDL or `prepare_database_migration`, so Prisma's migration history stays the source of truth.
- Ask before destructive SQL (`DELETE`, `UPDATE`, `DROP`, `TRUNCATE`), even on `development`.

## Security and auth

- Never cache the session at module level or behind an "initialized" flag: one process serves every user.
- Queries scope themselves to the session user: no `userId` threaded through callers. `userId` (or the user's own `id`) is part of every `where` for Item, Collection and User; another user's id finds nothing and is answered as not found.
- Call `requireCurrentUserId()` outside any `try`, so the sign-in redirect is not swallowed.
- `sessionVersion` is the real revocation check; the `jwt` callback stamps it only at sign-in; never let `update()` refresh it.
- The profile never carries the password hash or Stripe ids.
- Register answers a taken email exactly like a new one, so it cannot reveal whether an account exists.
- Redirect targets go through `safeCallbackUrl()` / `signInHref()`.
- Check email verification with `isEmailVerificationEnabled()`, never `process.env` directly.
- The sign-in rate limit lives in `authorizeCredentials()`, not the action, so a direct POST to the Auth.js callback is covered too.
- Auth pages call `redirectIfSignedIn()`, not bare `auth()`.
- The item drawer route (`GET /api/items/[id]`) answers 404 for a missing item and another user's item alike, and the drawer signs the user out on a 404.
- Services start with `import "server-only"` (except `services/prisma.ts`); only `services/` and `lib/db/` import the database client.

## Version pins

- Prisma stays on matching `^7` for `prisma` and `@prisma/client`: npm's `latest` tag points at an 8.x release candidate, so a bare `npm i prisma` installs 8.
- Vitest stays on `^4`: v5 needs `@types/node` 22+, and this project is on 20.
- Import the Prisma client from `@/generated/prisma/client`, not `@prisma/client`.

## Looks wrong, is not

- Keep the `@AGENTS.md` import at the top of CLAUDE.md.
- `AGENTS.md` is generated by `next dev`; durable guidance goes in CLAUDE.md.
- Read the local Next docs in `node_modules/next/dist/docs/` before writing App Router code; they override prior knowledge.
- `LayoutProps`, `PageProps` and `RouteContext` are global; do not import them or rewrite `LayoutProps<'/'>` by hand (for example into `{ children }: { children: React.ReactNode }`). It is the current, correct convention.
- There is no `tailwind.config.js` by design; `--font-sans: var(--font-sans)` is not a bug.
- `cn` comes from the `cn` package; do not reinstall `clsx` / `tailwind-merge`.
- Tests come before the code: write them from the feature's requirements, not from the code, and see each fail on its assertion before implementing. Once green, break the behaviour to prove each test can fail (full workflow in `context/ai-interaction.md`).
- Item detail is a drawer; do not add an `/items/[id]` page.

## Architecture

App Router under `src/app/`. Routes: `/` (still a placeholder), `/dashboard`, `/profile` and `/items/[type]` (one item type's items, e.g. `/items/snippets`) in the `(app)` route group, which shares the sidebar + top bar layout, and `/sign-in`, `/register`, `/forgot-password` + `/reset-password` in the `(auth)` route group, which shares a centered layout without adding a URL segment.

- **`src/app/layout.tsx`** is the root layout and is required — it owns the `<html>`/`<body>` tags, the font wiring, the always-on `dark` class, the default `metadata` export, and the Sonner `<Toaster theme="dark">` (pinned, since there is no `next-themes` provider).
- **Services own the connections; `src/lib/db/` is the interface.** Flow: actions / routes → `lib/db` → `services` → database. `src/services/prisma.ts` builds the one client, and only `services/` and `lib/db/` import it (`src/services/boundaries.test.ts` enforces this, and that `services/` never imports `lib/db/`). Every service file starts with `import "server-only"` except `prisma.ts`, which the seed loads in plain Node, and services hold no user-facing copy (wording lives in `lib/` and the UI). Outside API clients belong in `services/` too: `src/services/email.ts` is the email service, the only module that imports `resend` (send functions per email kind; templates stay in `src/lib/constants/emails.ts`), and `src/services/rate-limit.ts` is the rate limit service, the only module that imports `@upstash/*` at runtime (policies stay in `src/lib/constants/rate-limits.ts`; the blocked-caller message and `Retry-After` in `src/lib/auth/rate-limit-messages.ts`).
  - **`src/services/auth/`** is the auth service, split so its imports can't loop: `session.ts` (the session check: `getCurrentUser()`, `requireCurrentUser()`, `requireCurrentUserId()`, `redirectIfSignedIn()`; the only service that imports `@/auth`), `adapter.ts` (the Prisma adapter for `src/auth.ts`), `users.ts` and `tokens.ts` (the database side of sign-in, register, password change, verification and reset). They take plain arguments; bcrypt, expiry and cooldown rules, emails and rate limits stay in `src/lib/`. No `index.ts`: a barrel would bring the loop back.
  - **`src/lib/db/`** (`items.ts`, `item-types.ts`, `collections.ts`, `users.ts`): the CRUD functions the app calls. They build the query and shape the result into plain, UI-shaped types. Inside `(app)` the loaders are called by `getUserSession()`, except per-visit data such as recent items, which pages fetch.
- **`src/lib/` is grouped by area** (`boundaries.test.ts` checks the root): `auth/` (auth rules: register, sign-in check, password change and reset, verification, schemas, redirects, notices), `items/` (item schemas, type icons, the drawer's browser-side fetch), `session/` (user session and selectors), `helpers/` (generic: `format`, `slugify`, `form-errors`), `db/`, `constants/`. Only `utils.ts` stays at the root (shadcn's `components.json` points at `@/lib/utils`). Demo content for the seed lives in `prisma/seed-data.ts`, outside the app. Rules live in `lib/<area>/`; queries in `lib/db/`; connections in `services/`.
- **Types live in `src/types/`, one file per area**: `items.ts`, `collections.ts`, `session.ts`, `auth.ts`, `email.ts`, `forms.ts`, plus `next-auth.d.ts` (Auth.js augmentation). No `index.ts`; import each file directly. They are declarations only: the only imports allowed are `import type` from `@/types/` and `@/generated/` (e.g. Prisma's `Plan` enum). Code everywhere imports shapes from `@/types/...`, and components never import from `@/lib/db/`. Nothing outside `types/` exports a type, except the two calculated from a constant's value, which stay beside it: `RateLimitPolicy` and `Flag`. `boundaries.test.ts` enforces all of this.
- **The user session holds what rarely changes** (`src/lib/session/user-session.ts`, `server-only`). `getUserSession()` loads `{ user, itemTypes, itemCounts, pinnedItems, collections }`, cached per request, and is called **only by the `(app)` layout**, which runs on a full page load and on a reset, not on navigation. Items are not all in it: only counts (total, favorites, per type, counted in the database) and the pinned list. Collections are few, so all of them are, with item count and ranked types. `UserSessionProvider` (`src/components/session/`) holds it on the client; components read it with `useUserSession()` and derive display shapes with `src/lib/session/session-selectors.ts`. A test guards that the session is not cached across requests.
- **Not in the session, fetched per visit:** recent items (`getRecentItems()`, called by the dashboard page; pages re-render on navigation). Full item lists for "view all", editing and creating will load where they're needed.
- **Item detail is a drawer, not a page.** Clicking an `ItemRow` calls `openItem(summary)` from `useItemDrawer()`; `ItemDrawerProvider` (in the `(app)` layout) shows the card's summary at once and fetches the body from `GET /api/items/[id]` via `fetchItemDetail()`.
- **New items come from a dialog**, `ItemCreateDialog` behind the top bar's New Item button, offering only `CREATABLE_ITEM_TYPE_NAMES`. It and the drawer's edit mode render the same `ItemFormFields`, driven by `editableFieldsFor()`; the per-type rules live in that map, not in either form.
- **Updating the session:** `setUser` / `setItemTypes` / `setItemCounts` / `setPinnedItems` / `setCollections` from `useUserSession()` change it locally (for optimistic CRUD; the database save runs separately, and keeping counts and collection totals in step is the caller's job). `resetProfile()` reloads it from the server: from the hook on the client (`router.refresh()`), or from `@/lib/session/user-session` at the end of a server action (`refresh()`). A re-sent server session always replaces local state.
- **Queries scope themselves to the session user.** `lib/db` functions (and `changePassword`) each call `requireCurrentUserId()` (from `services/auth/session.ts`), which reads the per-request cached `getCurrentUser()` and redirects to sign-in when there is none. Scoping rules: see "Security and auth" under "Rules that must not change".
- **Auth is Auth.js v5 with a split config**: `src/auth.config.ts` (edge-safe, used by `src/proxy.ts`) and `src/auth.ts` (Prisma adapter, JWT sessions). The JWT carries only the user id and a `sessionVersion`; `getCurrentUser()` (`services/auth/session.ts`) reads the user row once per request (cached) and does two jobs: it is the auth check (guards, actions, auth pages) and the profile the user session holds (including `createdAt` and `hasPassword`). It also rejects a token whose `sessionVersion` is behind the user row's: password change and reset bump it, which signs out every other session (the proxy only verifies the JWT). Providers are GitHub and Credentials: `auth.config.ts` holds an edge-safe Credentials placeholder that `auth.ts` replaces with the bcrypt check from `src/lib/auth/authorize-credentials.ts`, and sets `pages.signIn`/`pages.error` to `/sign-in`. Sign-in, register and sign-out are server actions in `src/actions/auth.ts`; account creation lives in `src/lib/auth/register-user.ts`, shared with `POST /api/auth/register` (kept for non-browser clients). When the email is taken, the owner gets an email instead. Zod schemas live in `src/lib/auth/auth-schemas.ts`. `safeCallbackUrl()` / `signInHref()` live in `src/lib/auth/auth-redirect.ts`.
- **Email verification is on unless `EMAIL_VERIFICATION=off`.** `isEmailVerificationEnabled()` lives in `src/lib/auth/email-verification.ts`. Off skips the Resend email on register and the unverified-user block in `authorize`; users registered while off stay unverified and get a link on their next sign-in once it's back on.
- **Auth flows are rate limited** through `checkRateLimit(policy, headers, email?)` in `src/services/rate-limit.ts` (Upstash sliding window, policies in `RATE_LIMITS` in `src/lib/constants/rate-limits.ts`). It fails open: with `UPSTASH_REDIS_REST_URL`/`_TOKEN` unset, or Upstash down or slow, requests are allowed. The sign-in check lives in `authorizeCredentials()` and throws `RateLimitedError`, which the action turns into a message. Other actions check after validation and return `{ toast }` (`ActionForm` shows it as an error toast); the register route answers 429 with `Retry-After`.
- **Auth pages call `redirectIfSignedIn()`.** It sends a signed-in visitor into the app (their `callbackUrl`, else `/dashboard`), where the `(app)` layout loads the session. It checks the database, so a valid JWT whose user row is gone stays put instead of looping between `/sign-in` and the layout.
- **Forms are server-rendered with client islands.** Pages stay server components and pass a server action plus server-built fields to `ActionForm` (`src/components/shared/`), the one client boundary holding `useActionState`. `FormField`, `FormError` and `SubmitButton` are small client leaves that read its state. Actions return `FormState` (`src/types/forms.ts`). Prefer this over a whole `"use client"` form.
- **Components** are grouped by feature under `src/components/` (`auth/`, `dashboard/`, `collections/`, `items/`, `layout/`, `shared/`). `skeleton/` holds loading placeholders shaped like the content they stand in for, used as `<Suspense>` fallbacks around a page's slow query so the rest of the page renders first. `src/components/ui/` is shadcn-generated.
- **`@/*` maps to `./src/*`** (`tsconfig.json`).
- **`public/` does not currently exist.** For favicons and social images, prefer App Router metadata file conventions — `icon.png`, `apple-icon.png`, `opengraph-image.png` placed in `src/app/` get hashed URLs and auto-generated `<link>`/`<meta>` tags. Recreate `public/` only for assets that genuinely need a stable, hand-referenced path.

### Generated route types

Next generates the global `LayoutProps` / `PageProps` / `RouteContext` helpers from the actual folder structure into `.next/types/` and `.next/dev/types/` (both are in the `tsconfig.json` `include` array). They only exist after `next dev` or `next build` has run at least once. On a clean checkout, unresolved-type errors are expected until then — run a build before chasing them.

### Styling: Tailwind v4, configured in CSS

Tailwind v4 is configured from `src/app/globals.css` via `@import "tailwindcss"` and `@theme` blocks; PostCSS just loads `@tailwindcss/postcss`.

`globals.css` holds the shadcn setup: it imports `tw-animate-css` and `shadcn/tailwind.css`, defines the `dark` custom variant, the color and radius tokens, and the base `body` styles. Add or change design tokens there, not in a JS config.

Fonts: `layout.tsx` loads Geist and Geist Mono via `next/font/google` into `--font-sans` / `--font-mono` on `<html>`, and the `@theme inline` block binds them to the `font-sans` / `font-mono` utilities. `--font-sans: var(--font-sans)` works because `inline` writes the `var()` into the utility, which reads the value `next/font` sets.

### Constants: `src/lib/constants/`

User-facing strings and tunable values live in `src/lib/constants/`, one file per concern: `app.ts` (brand, title template), `routes.ts` (`ROUTES`, href builders, one-shot `FLAGS`), `limits.ts` (lengths, list sizes, link lifetimes, cooldowns), `security.ts` (bcrypt cost, dummy hash, token size, host and probe patterns), `rate-limits.ts`, `item-types.ts`, `emails.ts` (templates), `env.ts` (fallbacks and compared values), `time.ts` (ms units), `locale.ts` (html lang, date locale and zone), `ui.ts` (theme, toast id, avatar initials), `messages/` (`common`, `auth`, `account`). Add new ones there rather than inline.

- **Import each file directly; there is no `index.ts`.** Every file is data plus small pure formatters with no `process.env` reads, so any of them is safe in a client component. Env reads stay at their call sites as literal `process.env.NAME`.
- **Logic stays out.** `checkRateLimit`, `safeCallbackUrl`, `isEmailVerificationEnabled` etc. live where they did and import their values.
- **Text that states a value derives it.** Email and page copy says "expires in …" through `formatDuration(RESET_TOKEN_TTL_MS)`, never a typed "1 hour"; `minLength` uses `PASSWORD_MIN_LENGTH`.
- **Page titles** are just the page name (`title: "Sign in"`); the root layout's `APP_TITLE` template adds `| Stashboard`.
- **Stays inline on purpose:** JSX UI copy (headings, labels, button text), the `proxy.ts` `matcher` (Next reads it statically, so keep it in step with `ROUTES` by hand), `PageProps<"/route">` type arguments, `console.error` text, `src/components/ui/` and `src/hooks/` (shadcn-generated), and `prisma/seed-data.ts`.
- **`ROUTES` lists linked-but-unbuilt pages** (settings, collections, items); `routes.test.ts` keeps them in a `NOT_BUILT_YET` set and fails when one gets its page, so remove it from the set then.

### Class merging: the `cn` package

The [`cn`](https://github.com/shadcn-ui/cn) npm package is shadcn's drop-in replacement for `clsx` + `tailwind-merge`. The `ui/` files import it straight from `"cn"`; `src/lib/utils.ts` re-exports it for app code. Don't rewrite `utils.ts` back to the old wrapper.

### Database: Prisma 7 + Neon

- Config is in `prisma.config.ts`, not the schema: it loads `.env` via `dotenv` (Prisma 7 no longer does) and gives the CLI `DIRECT_URL` (unpooled). The app uses the pooled `DATABASE_URL` through the `PrismaNeon` driver adapter in `src/services/prisma.ts`, which is the only place a `PrismaClient` should be constructed.
- **Primary keys are UUID v4** (`@default(uuid())`, generated by Prisma, not a DB default; columns stay `text`). Don't hand-pick ids in seeds or fixtures. Match rows on natural keys (email, slug, name) instead.
- The client is generated into `src/generated/prisma/` (gitignored). `migrate dev` no longer runs `generate` for you. Run `db:generate` after schema changes if the dev server doesn't pick them up.

### Neon MCP and production

The Neon MCP rules and ids are under "Production and data" in "Rules that must not change". Production only changes when a merge to `main` triggers `db:deploy`.
